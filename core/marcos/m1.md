# Marco 1 — Definição da Necessidade

## Sub-agente corrente

**Claude Code:** orquestrador assume persona de `stakeholder-identifier` (carregar `core/agents/stakeholder-identifier.md` como contexto inline) e executa skills M1 diretamente no main context — sem Task() (D25, bug #12890/#34592).
**Gemini CLI:** adotar persona do `stakeholder-identifier`; carregar `core/workflows/m1-visao.md` como instruções adicionais.

## Tabela canônica — APENAS M1

**REGRA ABSOLUTA:** os únicos nomes de artefato válidos neste marco são:

| Arquivo | Tipo |
|---|---|
| `documentos-tecnicos/01-visao/01-visao-produto.md` | Normativo (interno) |
| `documentos-para-leigo/01-visao/01-visao-produto.md` | Leigo (aprovação Gate 1) |

**PROIBIDO criar** qualquer outro arquivo. Se a situação parecer exigir um arquivo diferente, parar e sinalizar ao orquestrador.

## Skills disponíveis neste marco

- `vision-box` — captura essência do produto
- `situacao-problema` — documenta o problema central (6 slots)
- `stakeholder-mapping` — mapeia pessoas envolvidas
- `contexto-e-limite` — define o que está dentro/fora do projeto
- `clarificacao-pos-visao` — resolve lacunas críticas pós-visão
- `traducao-leigo` — reescreve texto para remover jargão (transversal)
- `traducao-gate` — gera versão leigo para aprovação (transversal)

## Sequência canônica (modo Gemini CLI — chamada explícita)

Adapter `.gemini/` deve executar nesta ordem, chamando cada skill por nome explícito ("Use skill `X` agora"):

1. `vision-box`
2. `situacao-problema`
3. `stakeholder-mapping`
4. `contexto-e-limite`
5. `clarificacao-pos-visao` (condicional D16: ≥2 categorias com lacunas críticas)
6. `traducao-leigo` (verificação de jargão)
7. `traducao-gate` (gera `documentos-para-leigo/01-visao/01-visao-produto.md` + `documentos-tecnicos/01-visao/01-visao-produto.md`)
8. Executar C4.4 + C4.5; só então abrir Gate 1.

**Não aguardar auto-invocação por description-matching** — chamar cada skill explicitamente conforme a ordem acima (compensação para bug [google-gemini/gemini-cli#21968](https://github.com/google-gemini/gemini-cli/issues/21968)).

## Auto-checagem ao final de cada turno (C4.4 — Gemini fallback)

ANTES DE FINALIZAR O TURNO, verificar:
1. Foi escrita prosa para o usuário neste turno? Se sim → REFAZER como `AskUserQuestion`. Não publicar prosa.
2. Foi gerado algum arquivo neste turno? Verificar nome contra tabela canônica M1 acima.
3. Se nome inválido (ex: `necessidades.md`, `vision-box.md`, `fluxos.md`) → NÃO criar. Usar nome da tabela.
4. Se violação detectada → registrar em `estado-projeto.yaml.violacoes_detectadas[]` com timestamp + tipo.

## C4.5 — Verificação fail-closed de tabela canônica

Antes do PRE-FLIGHT do Gate 1, listar o diretório do projeto e cruzar com a tabela canônica de M1:

1. `ls <pasta-projeto>/documentos-tecnicos/01-visao/` e `ls <pasta-projeto>/documentos-para-leigo/01-visao/` → conjunto de arquivos presentes.
2. Para cada artefato OBRIGATÓRIO da "## Tabela canônica — APENAS M1":
   - Se `documentos-tecnicos/01-visao/01-visao-produto.md` ausente → `_pendencias.md`: `C4.5-MISSING: documentos-tecnicos/01-visao/01-visao-produto.md` + BLOQUEAR gate.
   - Se `documentos-para-leigo/01-visao/01-visao-produto.md` ausente → `_pendencias.md`: `C4.5-MISSING: documentos-para-leigo/01-visao/01-visao-produto.md` + BLOQUEAR gate.
3. Se qualquer arquivo presente tiver nome FORA da tabela canônica → violação C4.4 já captura; somar ao log.
4. Se qualquer C4.5-MISSING registrado → NÃO executar PRE-FLIGHT; RE-INVOCAR stakeholder-identifier.

C4.5 complementa o PRE-FLIGHT — PRE-FLIGHT verifica conteúdo; C4.5 varre o diretório exaustivamente contra a tabela.

## Gate 1 — Após M1

**PRE-FLIGHT CHECK OBRIGATÓRIO (executar ANTES de apresentar qualquer coisa ao usuário):**

```
VERIFICAR (obrigatório — bloquear se falhar):
  [ ] documentos-tecnicos/01-visao/01-visao-produto.md existe e não está vazio
  [ ] documentos-para-leigo/01-visao/01-visao-produto.md existe e não está vazio
  [ ] dados_projeto.nome ≠ "Ainda não definido" e ≠ vazio

SE qualquer verificação FALHAR:
  → escrever em estado-projeto.yaml: gate_1_bloqueado: "motivo"
  → RE-INVOCAR stakeholder-identifier para completar artefatos
  → NÃO apresentar gate ao usuário
  → NÃO marcar gate_1: aprovado

VERIFICAR blacklist D1 em documentos-para-leigo/01-visao/01-visao-produto.md:
  → invocar traducao-leigo sobre o conteúdo
  → se termos proibidos encontrados: reescrever antes de apresentar
```

**Ação do orquestrador (somente após pre-flight passar):**
1. Apresentar versão leigo ao usuário via `AskUserQuestion` (yesno):
   ```
   Aqui está o resumo do que documentamos sobre seu projeto:
   [conteúdo de documentos-para-leigo/01-visao/01-visao-produto.md]

   Está correto? Posso seguir para a próxima fase?
   ```
2. Se SIM: registrar em `versao_leigo_aprovada[]`, atualizar `estado-projeto.yaml`, avançar M2
3. Se NÃO: retornar ao `stakeholder-identifier` com feedback do usuário; **não** avançar marco

**INVARIANTE:** `gate_1_status: aprovado` só pode ser escrito em `estado-projeto.yaml` após `AskUserQuestion` retornar SIM.
